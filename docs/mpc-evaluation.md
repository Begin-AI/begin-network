# Three-party secure predicate evaluation

Experiment run: 2026-10-14. Runnable artifacts are in [experiments/mpc](../experiments/mpc/README.md). This is a synthetic passive-security experiment, not an approved private discovery method or a P2 claim.

## What was run

MPyC 0.11 was installed from its pinned SHA-256 wheel in `/tmp/begin-mpc-env`, using uv-managed CPython 3.12.13. The [official MPyC source](https://github.com/lschoe/mpyc) describes Shamir-based multiparty computation against a passive dishonest minority, with `t < m/2`. Three parties with threshold one therefore assume at most one passive corruption. The MIT-licensed package has no mandatory third-party dependencies in this experiment. [PyPI release](https://pypi.org/project/mpyc/0.11/) and the checked wheel hash are recorded in `experiments/mpc/requirements.txt`.

The controller launched three separate Python processes with explicit `-I` indices and `-P 127.0.0.1:port` addresses. It did not use MPyC's automatic local-party spawning. Each process had a separate temporary working directory and read only its own `input.json`. Party 0 received only requester rows; party 1 received only owner rows; party 2 received `null` rows and supplied no private values. The circuit process's source contains no complete fixture corpus. The controller knows all synthetic fixtures to calculate gold outputs; all parties share one OS user/machine. This is protocol-input separation, not host or filesystem isolation.

The circuit uses three 32-coordinate quantized vectors per party, representing separate mirror/window/social slots. It computes a secret dot product across all 96 coordinates and a combined secret predicate. The predicate includes requester/helper complementary roles, language equality, both willingness bits, requester budget ≥ owner required units, coordinate range checks and threshold ≥1,500,000. Coordinates are checked within ±1000 in the circuit. `SecInt(48)` comfortably bounds the intended 96-term score (absolute maximum 96,000,000), with bounded constraint fields. Inputs are synthetic integer fixtures, not learned embeddings.

Only the combined boolean is opened to parties 0 and 1 through `mpc.output(..., receivers=[0,1])`; helper party 2 receives no opened result. The runner asserts this and requires equality to the plaintext predicate for every case. It does not open the score, individual role/constraint results, or vectors.

## Observed evidence

[Recorded results](../experiments/mpc/results.json) contain circuit source SHA-256, platform, Python/MPyC versions and three distinct PIDs. Ten of ten predicates matched for both authorized output recipients; the helper reported ten `null` outputs and zero private rows. Cases covered the exact threshold, a one-coordinate increment/decrement, wrong role, language mismatch, owner/requester refusal, budget excess, out-of-range coordinates and negative similarity. Six regression tests pass: four test classes launch all three parties independently (12 subprocesses) and confirm altered circuit hash, missing consent, a genuinely signed mismatched consent digest and expired session abort before `mpc.start`; two plaintext tests verify the fixed gold outcomes and willingness rejection despite high score. These tests do not substitute for the actual three-party run.

Measured on Apple Silicon/macOS 26.6.2: 4.625 seconds wall time for the ten-case batch; approximately 4.376 seconds in each party's protocol section. MPyC counted 9,098,640 / 9,098,420 / 9,078,400 bytes sent by parties 0/1/2 before shutdown, totaling 27,275,460 bytes. These are library protocol byte counters, not packet-capture traffic or complete wire overhead; shutdown and TCP framing are excluded. No claim of optimized throughput, mobile energy performance or wide-area latency follows from a single loopback batch.

## What each party can learn, and limitations

Parties 0 and 1 learn their own input and final boolean, plus public circuit parameters, session sizes and traffic metadata. The helper learns public topology, sizes and traffic metadata and receives secret shares, but no opened boolean under the stated passive one-corruption model. Two colluding parties exceed the model and can compromise privacy. An actively malicious party, arbitrary oversized field inputs, modified circuit or dishonest output is outside this experiment's guarantee; in-circuit ranges do not upgrade the passive protocol to malicious security.

Transport used loopback TCP **without TLS**. A privileged host/network observer and the controller are outside the claimed model. Separate independently administered hosts require pinned authenticated channels, explicit key/session/circuit agreement and tests before this evidence can apply there. The experiment now verifies Begin-signed unanimous session agreement before computation, as detailed below. It has no authorization ledger integration or transferable proof of correct computation. A boolean result creates no permission and cannot itself release a sealed request.

Adaptive boolean probes can still infer private information. Query policy and identity limitations remain unresolved; a limit per key does not stop many-key requesters. The static fixture roster does not implement private candidate enumeration, coordinator routing, hidden group membership or multi-owner ranking. The run demonstrates private pairwise computation building blocks useful for the patent's distributed discovery architecture; it does not prove the complete network.

## Next mechanism decision

Keep this MPyC path as a reproducible honest-majority baseline beside owner-local encrypted matching. Compare the same predicate against a malicious-secure MP-SPDZ path under its actual adversary assumptions, then test independently administered machines. Extend the signed circuit/session agreement to authenticated distributed transport and persistent replay policy; add locally chosen helper policy, authorization before computation, refusal/abort handling, real encoder quantization/error evaluation and adaptive probing assessment. Preserve the brief's mutual authorization and private intentions: none of these experiments justifies publishing vectors or treating similarity as consent.


## Signed session agreement before MPC

Each party's locally trusted fixture configuration pins three participant public keys. The controller generates these synthetic independent identities and retains private signing keys only in memory; no private signing keys appear in command arguments, reports or per-party files. Every party receives all three consent tokens, then independently uses the noneditable installed Begin verifier to check signatures, issuer key binding, audience and validity. There is no Begin/company signing authority. The package was locally built and installed into the experiment environment; results record its version, cryptography version and the installed verifier source SHA-256 for provenance.

All three sign exactly the same session digest, which covers the session ID, issued/expiry times, party.py and session.py hashes, model revision, dimensions/slots, quantization bounds, secure-integer width, threshold, passive corruption threshold, MPyC version, statistical security parameter and PRSS mode, exact three-party addresses/key IDs, output receivers, transport policy and case count. Each party compares the signed hashes to its own source files and signed topology to its actual MPyC configuration. Missing/duplicate signers, divergent consent, unsupported parameters or expiration are rejected before the runtime connects. The maximum lifetime is 300 seconds. The successful result reports the same consent digest from all three processes.

This is experimental participant consent under local fixture trust policy, not authority to spend a resource, execute arbitrary remote code or override a human's host policy. Pinning keys is a host action: importing a peer's replacement keys alongside its tokens would defeat the trust boundary. Consent does not bind actual private input truthfulness, establish a transferable computation proof, or prevent an authorized participant rerunning a still-valid session. Persistent replay, live revocation, distributed identity selection and authenticated TLS transport remain separate work. The passive protocol and same-host/controller limitations still apply.
